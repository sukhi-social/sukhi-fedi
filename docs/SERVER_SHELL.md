# サーバーシェル(`sukhi`)設計

> 状態: **設計のみ。実装はまだない。** 運用者が、人でも AI でも、同じ入口から
> サーバーのバージョンアップと簡易スクリプトの実行をできるようにするための設計書。
> 最後の §12 に、決めたいことを選択肢と推奨つきでまとめた。

## 0. この文書の読み方(曖昧だった点)

依頼は「使いやすいサーバーシェル(人にも AI にも、MCP 対応)。バージョンアップと簡易スクリプト実行など」。
次の読みで進めた。違っていたら §12 の Q1 で直す。

- 対象は **sukhi-fedi の運用者向けの管理シェル**。汎用の SSH シェルの代わりではない。
- 形は二つ。ホストで叩く CLI `sukhi`、そして BEAM の中で動く操作の登録簿(以下 **Ops**)。
- 主な対象リリースは `combined`(gateway + delivery + api を一つの BEAM に入れたもの)。
  分割構成の `gateway` でも同じ Ops が動く。
- 主軸の前提は、プロジェクト方針どおり **Datalevin(`SUKHI_STORE=datalevin`)**。
  Postgres は「動くまま維持」で、新機能の対象にしない(§7 で差分だけ書く)。

| デプロイ | combined-sha.yml が main ごとに sha タグを GHCR へ、haloy が本番へ。Watchtower は自前ホスト向け(SETUP.md「Upgrades」) | 自動で更新される | 「今の版は何か」「更新前に確かめる」「戻す」の入口がない |

**所見。** 部品はそろっていて、足りないのは「ひとつの登録簿」と「境界での認証・権限・監査」。
`rpc` をそのまま AI に渡すのは危ない(任意コード実行になる)。だから AI にも人にも、
**名前のついた操作だけ**を出す。これは CODE_STYLE の規則(§0:安全性は一か所に置き、構造がすべての経路をそこへ通す)の、運用面への適用。

## 2. 全体像

```
 人 ──▶ sukhi (ホスト側の薄いスクリプト) ─┐
 AI ──▶ sukhi mcp (stdio の MCP サーバー) ─┤  どちらも同じ線:
 他 ──▶ HTTP /admin-api (トークン,任意) ───┤
                                          ▼
                    Unix ドメインソケット(コンテナ内、0600)
                                          ▼
                     SukhiFedi.Ops.Gateway   ← 認証・権限・監査はここ「だけ」
                                          ▼
                     SukhiFedi.Ops.Registry  ← 操作の登録簿(単一の正本)
                                          ▼
          Release / Maintenance.* / Store / Version … (既存の文脈モジュール)
```

三つの原則。

1. **操作は一か所で定義する。** CLI のサブコマンド、MCP のツール、`--json` の形、
   ヘルプ文、権限の段階は、すべて Registry の一つの宣言から作る。
   表面ごとに別実装を持たない(増えると必ずずれる)。
2. **境界で一回だけ確かめ、内側は信じる。** 認証・権限・監査・タイムアウト・
   同時実行の制限は `Ops.Gateway` のみ。各操作はそれを覚えていなくてよい。
3. **既定は安全側。** 変更系は何も言わなければ dry-run。実行には明示の `--execute`(MCP では承認)が要る。

## 3. 操作の宣言(Registry)

各操作は、次のような宣言を持つ。

```elixir
%Op{
  name: "script.run",
  summary: "登録済みスクリプトを実行する",
  level: :mutate,            # :read | :plan | :mutate | :dangerous
  args: [name: :string, mode: {:enum, [:dry_run, :execute]}, opts: :map],
  concurrency: {:exclusive, :maintenance},   # 同時に走らせてよい範囲
  timeout_ms: 3_600_000,
  run: &SukhiFedi.Ops.Script.run/1,
  output: schema        # --json と MCP の戻り値の形。人向け整形も同じ構造体から作る
}
```

- `level` は §8 の権限の段階と一対一。
- 戻り値は必ず `{:ok, map}` か `{:error, %{code, message, hint}}`。人向けの表は同じ map の描画で、`--json` はそのままの map。
  AI は文字列の解釈をしなくてよい。
- 秘密を含みうる項目は schema に `secret: true` と書き、描画の前に取り除く(§8)。

## 4. 人向け CLI

ホストで叩く `sukhi`(bash の薄いスクリプト。中身は `docker compose exec` でコンテナ内の
`bin/combined rpc` → ソケットの呼び出しに変える。Erlang の cookie を人が扱わなくて済む)。

```
sukhi status                  # 版・稼働時間・store・キュー・直近のマイグレーション
sukhi version                 # 現在版 / 最新版 / 差分(取得だけ。変更しない)
sukhi upgrade [--to 0.4.15]   # 計画を出す(dry-run)。--execute で実施
sukhi rollback [--to 0.4.14]  # 同上
sukhi migrate [--execute]     # Datalevin では「やることなし」と理由つきで返す
sukhi store info              # 種類(datalevin/postgres)、場所、サイズ、スキーマ版、直近バックアップ
sukhi script list             # 登録済みスクリプト、説明、dry_run の有無
sukhi script run <name> [--execute] [--timeout 30m] [-- 引数]
sukhi script runs [<id>]      # 実行履歴、進み具合、終了状態
sukhi script cancel <id>
sukhi audit [--since 1d]      # 監査ログ
sukhi shell                   # 対話モード(下記)
sukhi mcp                     # MCP サーバーを stdio で起動(§6)
sukhi completion bash|zsh|fish
```

使いやすさの決まり。

- **dry-run が既定。** 変更系は「何をするか」の計画を出して止まる。`--execute` で本番。
  計画には対象件数・所要見込み・戻せるか・必要な前提(バックアップがあるか)を載せる。
- **確認プロンプト**は `:mutate` 以上で、`--execute` のとき端末なら一回だけ。「もう一度 y と打つ」ではなく、
  対象を言い直させる(例: `upgrade` なら版の番号)。`--yes` で省略できるが、`:dangerous` は省略できない。
- **出力**は端末なら整形、パイプなら自動で JSON(`--json` / `--no-json` で強制)。
  終了コードは 0 成功、1 失敗、2 使い方の誤り、3 権限不足、4 計画のみで未実行(スクリプトから判定できる)。
- **補完**はサブコマンド、スクリプト名、`--to` の版を動的に補う(`script list` / `version` を呼ぶ)。
- **エラーには次の一手**を書く(`hint`)。例:「`maintenance` ロックを別の実行が持っています。`sukhi script runs` で確認」。
- **対話モード**(`sukhi shell`)は、同じ Ops を呼ぶだけの REPL。履歴と補完があり、IEx のような任意の式評価は**出さない**。
  どうしても必要なときの非常口は別に残す(§7.1)。

## 5. バージョンアップ

### 5.0 いまの経路(ひなたの説明 + `.github/workflows/combined-sha.yml`)

焼くのは GitHub Actions。main への push ごとに、`combined` / anubis / natadeco-ssr / web-next の
四つが、同じ commit の `sha-<commit>` というタグで GHCR に出る(arm64)。デプロイだけが手動:

```
[自動] main に push → combined-sha.yml → ghcr.io/…:sha-<commit>
[手動] sukhi-deploy の haloy.yaml のタグを新しい sha に書き換える
[手動] haloy deploy -t sukhi-fedi-app      ← 起動時に entrypoint が migrate_all() を実行
[公開] タグ v*.*.* → release.yml → GHCR の semver / latest(公開 multi-arch。本番は使わない)
```

`bin/build-on-box.sh`(箱で焼く経路)は、いまの本番では使っていない前提で扱う。
Watchtower は公開 compose で自前ホストする人向けで、本番とは別。

手順は短いので、面倒の正体は手順の数ではなく **「人が覚えて、人が目で確かめる」** ことだと見ている。

| 面倒 | 中身 |
| --- | --- |
| 「どの sha を上げるか」を人が選ぶ | main の最新か、動作確認した sha か、GHCR を見に行って写す |
| 書き換えが別リポジトリ | タグ(sha)を sukhi-deploy の haloy.yaml に手で書く。三つの image を同じ sha に揃える必要がある |
| 事前の確認がない | その sha の build が成功したか、バックアップが新しいか、マイグレーションがあるか |
| 事後の確認がない | 新しい版が動いているかは、見に行く |
| 記録がない | いつ・誰が・どの sha を上げたか、戻す先の sha が残らない |
| 二重の仕組み | 本番は haloy、自前ホストは Watchtower |

> haloy 側の機能(ロールバック、ヘルスチェック、image の指定方法)は、公開ドキュメントの要約でしか確かめていない。
> `sukhi-deploy` はこのセッションから見えないので、**haloy.yaml の中身は未確認**(§12 Q9)。

### 5.1 目指す形: 「sha を選んで、確認して、押す」だけにする

haloy も GitHub Actions もそのまま。**haloy の前後を `sukhi release` が包む。** haloy は「入れ替える」役、
sukhi は「入れてよいかの判断・記録・確認」の役。タグの書き換えも `sukhi release` がやる。

```
sukhi release                 # 候補の sha(既定は main の最新で build が成功したもの)の計画を出して止まる
sukhi release --sha abc1234   # sha を指定
sukhi release --execute       # 版を打ち直して実施
sukhi release status|history|rollback
```

`--execute` の中身:

1. **候補を決める**: GitHub の check から「build が成功し、四つの image がそろっている sha」を選ぶ。
   一つでも欠けていれば出さない(「同じ sha どこでも」の約束を守る)。
2. **事前チェック**(§5.2)。失敗なら理由と次の一手を出して止まる。
3. **タグの書き換え**: haloy.yaml の三つ(四つ)の image を同じ sha に揃える。ダイジェストも取って記録する。
4. **デプロイ**: `haloy deploy -t <target>`。
5. **事後の確認**: 新しい版の名乗り、`status`、キュー、エラー率を一定時間(既定 5 分)見て、結果を一画面にまとめる。
6. **記録**: 監査表(§8.4)に一行。戻し先の sha も同じ行に残る。

### 5.2 責任を取れる UX(管理者が「何を承知したか」を残す)

「手間をなくす」ことと「確認を省く」ことを同じにしない。**確認の回数は減らし、確認の質は上げる。**

- **計画は一画面で読める**。次のものを並べる。
  - 何を上げるか: 現在版 → 新版、commit、変更の要約(前回のデプロイからの `git log` の件名)、ダイジェスト
  - データへの影響: マイグレーション有無(Datalevin はなし)、スキーマ変更、戻せるか(§5.6)
  - 前提の状態: 直近のバックアップの時刻と検証結果、ディスク残量、キューの滞留、実行中のスクリプト
  - 止まる時間の見込み(combined は一つの BEAM なので、再作成の間は短く止まる)
- **確認は一回、版の番号を打ち直す**。「y」ではなく、`0.4.15` と打つ。流し読みで通らない。
  `--yes` は `:mutate` までで、データに触れる変更(戻せない計画)には使えない。
- **前提が満たされない場合は止まる。管理者が理由を書いて進める道は残す**(`--accept-risk "理由"`)。
  理由は監査に残る。止まるだけだと別の経路(手打ちの haloy)に逃げられて、記録の外に出るため。
- **事後は「見ておくべきこと」を勝手に探してくれる**。デプロイ後の窓の間、エラー率・キュー・版を見て、
  悪化が見えたら「戻しますか」と**提案**する。自動では戻さない(§5.6)。
- **記録は追記専用**。誰が(トークン名または端末の主体)、いつ、どの commit とダイジェストを、どの計画のもとで、
  どんな結果で上げたか。「責任を取る」ための材料を、取る側が後から読める形で残すのが目的で、責める道具にはしない。

### 5.3 経路の選択肢

build はすでに自動なので、残る選択は「デプロイの手動をどこまで減らすか」。

| 案 | 内容 | 手間 | 注意 |
| --- | --- | --- | --- |
| **P(推奨・第一段)** | `sukhi release` が sha の選択・事前事後の確認・タグの書き換え・記録までを包む | 「sha を見て、確認して、押す」の一回 | sukhi-deploy の書き換え方(同じリポジトリに commit するか)を決める |
| R | main の build 成功後に、承認の関門つきで自動デプロイ | 押す手間もなくなる | 責任の置き場が「承認」に移る。承認が形だけになる日が出る。事後確認と記録が安定してから |

推奨は **P**。R は、P の事後確認と記録が安定してから。

### 5.4 自前ホスト(Watchtower)の人たち

Watchtower は公開 compose の利用者向けで、本番とは別。同じ「更新」を二通りにしないために、
`sukhi upgrade`(compose 用)を同じ計画・記録の形で提供する。

- 既定は**通知のみ**: 新しい版があることと計画(§5.2)を見せ、人が `--execute` する。
- 自動更新を望む人は、今までどおり Watchtower を使える。ただし更新前チェックは働かない、と書いておく。
- 実施は `docker compose pull && up -d`。ダイジェスト検証は §5.5 のとおり。

### 5.5 検証

- 既定はダイジェスト固定(`@sha256:`)。`sha-<commit>` のタグが指すダイジェストを計画の時点で取り、記録する。
- 公開 image(GHCR)は、署名(cosign)が CI で付くまでは「ダイジェストが公開メタデータと一致」までを検証とし、**未署名と明示**。

### 5.6 マイグレーションとロールバック

| | Datalevin(主) | Postgres(維持) |
| --- | --- | --- |
| マイグレーション | なし。スキーマは `priv/datalevin/catalog.exs` から導き、store を開くときに入れる(`Release.migrate_all/0` は何もせず返す) | `migrate_all/0`。`check_migration_sanity/0` が順序の狂いを止める |
| 更新前の安全網 | `dtlv` のコピー(スナップショット)を必ず取る | `pg_dump` 相当(既存の backup を使う) |
| 戻し | 前のイメージへ戻す。スキーマ追加だけの変更なら読める見込み。**非互換の変更があった版は、スナップショットから戻す** | マイグレーションは前進のみ。戻しは「前のイメージ + バックアップから復元」。down は書かない |

戻しは**人の判断**を挟む。自動ロールバックは、書き込みの多いサーバーではデータを失いやすい。
`sukhi rollback` は、(a) 前のイメージへ戻すだけで足りるか、(b) スナップショットの復元が要るか、
(c) 復元でどの時点までのデータが消えるか、を計画に書いてから止まる。
この「互換性があるか」の判定は、リリースごとに `compat` の宣言(最低限の戻り先の版)を持たせる案が自然だが、
まだ設計していない。**未確認の点として §12 Q5 に残す。**

### 5.7 Alpine イメージとローリング

- リリースイメージは Alpine(musl)。シェル用の追加パッケージは**入れない**。
  コンテナ内の部品は BEAM だけで完結させ、ホスト側スクリプトは bash と docker CLI だけに依存する。
- ローリングは分割構成(gateway と api を別コンテナで持つ構成)でだけ意味がある。
  `combined` は一つの BEAM なので、止まる時間が短く出るだけ(再作成の間)。
  ARCHITECTURE の規則で gateway と api は **cookie を同時に更新**する必要がある(ENV.md)。
  版の組み合わせも同じで、分割構成では「api → gateway」の順に上げ、互換のない版の組み合わせを計画の段階で拒否する。

### 5.8 ブラウザからのデプロイ(信頼の二段 + 事前告知 + 時刻指定の更新)

> 要望: 実行役はサーバー。一次の信頼は「特定のリポジトリからビルドされたもの」(sigstore 的)、
> 二次の信頼はサーバー上のパスキー認証。そのあと自動で告知し、数分後に再起動して更新する。

管理画面(`/admin/release`)と CLI(`sukhi release`)は、同じ依頼を出すだけにする。
実際の入れ替えは、サーバー上の **updater**(アプリのコンテナの外、ホスト側の小さな常駐役)が行う。

```
管理者 ─ タグを入力 ─▶ アプリ: 計画(§5.2)を出す
管理者 ─ 版を打ち直す + パスキーで承認 ─▶ アプリ: 依頼を updater に渡す
                                            ▼
updater: ① 一次の検証(sigstore)  ② 二次の検証(パスキーの承認)
         ③ 告知を出す(N 分前)  ④ 取り消し可能なカウントダウン
         ⑤ 事前チェックをもう一度  ⑥ haloy deploy(ダイジェスト指定)
         ⑦ 事後の確認  ⑧ 結果の告知 + 監査
```

#### 一次: 「このリポジトリの、この workflow が焼いたもの」だけを信じる

- 入力は **タグ文字列だけ**(`sha-<7〜40桁>` か `v<semver>`)。image 名とレジストリは固定。
- updater は、タグを **ダイジェストに解決**し、以降はダイジェストだけを扱う(検証と実行の間にタグが動いても、別物は入らない)。
- 検証は sigstore の keyless 署名。updater は次を確かめる:
  - 署名者の身元が `https://github.com/sukhi-social/sukhi-fedi/.github/workflows/combined-sha.yml@refs/heads/main`(= 本リポジトリの main の workflow)であること
  - 発行者が GitHub Actions の OIDC(`https://token.actions.githubusercontent.com`)であること
  - 対象のダイジェストが、四つの image(combined / anubis / natadeco-ssr / web-next)すべてで同じ commit のものであること
- **main 以外のブランチからの build(`refactor/web-batches`、手動実行)は信じない。** いまの `combined-sha.yml` は
  それらにも `sha-` を出すので、身元の `@refs/heads/main` で区別する。
- 秘密の鍵を管理しない(keyless)ので、「鍵が盗まれる」という事故の形がない。信頼の根は GitHub と Fulcio/Rekor の透明性ログ。
- **現状との差:** いまの CI には署名の工程がない(リポジトリを確かめた限り)。**CI に署名(cosign の keyless、または GitHub の build provenance 証明)を足すのが前提条件。**
  これが入るまでは、updater は動かさない(検証できないものを入れない)。

#### 二次: サーバー上のパスキー

- 既存の `Auth.Passkeys`(Wax、ユーザー検証必須、使い捨て challenge)を再利用する。
  `purpose: "release"` の challenge に **計画のハッシュ(ダイジェスト・現在版・実行予定時刻)を混ぜる**。署名されるのは「この計画」であって、ログイン中の誰かではない。
- セッションが生きていても、その場でパスキーを求める。有効は 5 分、使い捨て。
- 条件: `is_admin`、パスキー登録済み(未登録ならボタンを出さず、登録へ案内)。
- **どこで検証するか(段階):**
  - 第一段: アプリが Wax で検証し、承認記録(管理者 id、credential id、計画のハッシュ、時刻)を updater との共有の鍵で署名して渡す。
  - 第二段: パスキーの署名(assertion)そのものと challenge を updater に渡し、updater が管理者の公開鍵で自分で検証する。
    アプリが乗っ取られても、パスキーなしでは承認を偽造できない。
- 一次と二次は**別の問い**に答える。一次は「何を入れてよいか」、二次は「誰が入れると言ったか」。どちらかだけでは入れない。
  アプリが乗っ取られても(二次が偽造されても)、入れられるのは「このリポジトリの main が焼いた、署名つきの image」だけ。

#### 告知 → カウントダウン → 更新

1. **告知**: 承認された時点で、既存の `Announcements`(公開期間つき、ローカル限定)に「N 分後に更新します(予定 HH:MM、短い再起動があります)」を自動で作る。
   公開期間の終わりは実行予定時刻の少しあと。web-next にも同じ告知が出る。通知(Web Push)を使う場合は、任意で同じ文を送る。
2. **カウントダウン**: 既定 10 分(5〜60 分で指定)。updater が時刻を持つので、アプリが再起動しても続く。
   - 管理者は、パスキー承認で**取り消し**と**延長**ができる。
   - カウント中に別の依頼が来たら拒否する(同時に一つ)。
   - 新しい版が出た(計画の前提が変わった)ときは、依頼を失効させて、計画を取り直させる。
3. **直前のチェック**: 実行の時点でもう一度、バックアップの新しさ、キューの滞留、ディスク残量、実行中のスクリプトがないことを見る。
   失敗したら実行せず、告知を「見送りました」に書き換えて、管理者に知らせる。
4. **更新**: `haloy deploy` をダイジェスト指定で呼ぶ。起動時に `migrate_all()` が走る(Datalevin はなし)。
5. **事後**: 新しい版の名乗り、`status`、キュー、エラー率を一定時間見る。悪化なら戻しを**提案**する(自動では戻さない)。
   告知を「更新しました(版)」に書き換え、監査に追記する。

#### 守り

- updater が持つもの: haloy の API トークンと docker の権限。**アプリは持たない。** アプリと updater の間は、ホスト内の Unix ソケット(0600)か、書き込み専用の依頼ディレクトリ。
- updater は小さく保つ。仕事は「検証して、待って、haloy を呼ぶ」だけ。受け取る入力は、タグ文字列・承認記録・時刻のみ。
- **ダウングレードは別の確認**: 現在より古い版は、`rollback` として別の計画・確認を通す(戻し先は監査に残したダイジェストから選ぶ)。
- 監査: 入力タグ、解決したダイジェスト、署名の身元、承認した管理者と credential id、告知の id、実行時刻、結果。
- 失敗の既定は「入れない」。検証できない・時刻を過ぎた・チェックが落ちた、のどれでも実行しない。

#### 将来: 自動で適用する

一次の信頼が確立すると、「main の build が成功したら、条件を満たすものを自動で告知 → 適用」も安全に作れる
(例: 夜間の窓の中だけ、パッチ版だけ)。ただしこれは責任の置き場を「承認」から「方針」に移すので、
手動の流れ(上)が安定してから、別に決める。

### 5.9 世の中の updater(定番)と、自前の updater の位置づけ

調べた範囲(比較記事 1 本と一般的な知識。**各ツールの署名検証の有無は、各公式ドキュメントでは未確認**)。

| ツール | 役割 | 更新のしかた | 署名(sigstore)の検証 | 本件との関係 |
| --- | --- | --- | --- | --- |
| Watchtower(原版) | レジストリを見て、コンテナを自動で入れ替える | 自動 | 記事には記載なし | **2025-12-17 に archive 済み(読み取り専用)。** SETUP.md が案内している自前ホスト向けの自動更新の前提が崩れている |
| Watchtower の fork(nicholas-fedor/watchtower) | 原版の保守 fork | 自動(既定は 24 時間ごと) | 記載なし | 自前ホストの代替候補。ただし署名の検証がない |
| Diun | レジストリを見て**通知するだけ** | 通知のみ | 記載なし | 「新しい版が出た」の知らせには使える |
| WUD(What's Up Docker) | 画面つき。パッチ版までは自動、大きな更新は通知 | しきい値つき自動 | 記載なし | 方針(パッチだけ自動)の考え方が近い |
| Tugtainer | 画面つき。コンテナごとに通知/自動を選ぶ | どちらも | 記載なし | 作者が「本番向けではまだ」と言っている |
| dockcheck / Cup | ダイジェストの比較を行うスクリプト / 検査器 | 手動選択 / 通知 | 記載なし | 軽いが、承認と記録はない |
| haloy(本番) | 配備の入れ替え | 手動で実行 | 未確認 | 入れ替える役として残す |
| Flux / Argo CD Image Updater + 署名検証の方針(Kubernetes 側) | image の更新と、署名の検証を方針にできる | 自動 | あり(cosign 系) | k8s 前提で、この箱には重い。**考え方だけ参考にする** |

**読み取れること**
1. 定番の updater は「新しい image を入れる」ことが仕事で、**「誰が焼いたかを確かめる」「人が承認する」「事前に告知する」「記録する」は持っていない**(少なくとも記事の範囲では)。ここが自前の updater の価値になる。
2. 自前ホスト向けの自動更新は、Watchtower の archive で選び直しが必要。§5.4 の「通知のみ(Diun 相当)を既定にする」は、この点でも理にかなう。
3. 入れ替える部分(haloy や compose)は作り直さない。updater は**検証・承認・告知・時刻・記録**だけを持ち、入れ替えは既存のものに渡す。

**リポジトリの現状(確認したこと)**: `sigstore` / `cosign` / provenance の記述は、リポジトリ内のどこにもない(今回の設計書を除く)。
`combined-sha.yml` と `release.yml` は、image を GHCR に push するだけで、署名はしていない。
別のリポジトリ(sukhi-deploy など)や、他の仕組み(Docker Content Trust など)で署名の話があったなら、教えてほしい。

### 5.10 第 0 段: SSH で入って、一本のスクリプトを実行する

> 提案(ひなた): サーバーへの SSH を親切なドキュメントに書き下ろし、「サーバーで認証したあとは、このスクリプトを実行してね」とする。
> サーバー管理者なら、シェルの使い方は理解しておいたほうがいい。

これを**最初の入口**にする。画面(§5.8)や AI(§6)より前に、これだけで更新できるようにする。

- 認証は SSH(鍵)に任せる。アプリ側にデプロイの認証・権限・画面を作らなくてよい。**作るものが最小で、攻撃面が増えない。**
- 入ったあと実行するのは、**§5.1 の `sukhi release`(計画 → 版の打ち直し → 実行)**。中身は §5.1〜5.5 のとおり。
  人が読む案内は [`OPERATING_OVER_SSH.md`](OPERATING_OVER_SSH.md)。
- 理解してから使う前提なので、画面より**説明が長く、確認が丁寧**でよい。責任の取り方(§5.2)は同じ。
- 後から足す画面(§5.8)や MCP(§6)は、**同じスクリプトを呼ぶ別の入口**にとどめる。updater が二つの更新の仕方を持たない。
  SSH 入口が先にあることで、画面が壊れた夜にも更新と戻しができる(最後の砦)。
- 一次の信頼(署名の検証、§5.8)は、SSH 入口でも同じく働かせる。「サーバーに入れる人なら何でも入れてよい」とはしない。
  SSH は「誰が」を答え、署名は「何を」を答える。

**実装の順番(§10)の先頭に置く:**
`sukhi status|version|release(計画のみ)` と CI の署名 → `release --execute` と記録 → 告知とカウントダウン → 画面・MCP。

## 6. AI 向け: MCP

### 6.1 公開のしかた

- `sukhi mcp` は **stdio の MCP サーバー**。AI クライアント(Claude Code など)は、
  ホストまたは SSH 先でこのコマンドを起動するだけで使える。HTTP を外に開けなくてよい。
- 中身は §2 のソケットを呼ぶだけ。MCP のツール定義は Registry から**自動生成**する(別に書かない)。
- 将来、遠隔から使うために streamable HTTP を足す余地は残すが、既定では出さない(§12 Q2)。

### 6.2 ツールの切り分け

MCP のツールは level で**別のサーバー設定**に分ける。クライアントが読み取り専用のほうだけ繋げば、
変更系は定義そのものが見えない。

| 接続名 | 含むもの | 既定 |
| --- | --- | --- |
| `sukhi-ro`(読み取り専用) | `status`, `version`, `store_info`, `script_list`, `script_runs`, `audit`, `upgrade_plan`, `rollback_plan`, `script_plan`(dry-run) | 有効 |
| `sukhi-rw`(変更系) | `upgrade_apply`, `rollback_apply`, `script_run`(execute), `script_cancel` | 無効。トークンの段階が `:mutate` 以上のときだけ |

ツール名は動詞つきの短い名前、説明は「いつ使うか・いつ使わないか」まで書く。
引数は enum と型で固め、自由な式は受け取らない。

### 6.3 承認と安全

- **plan と apply を別のツールにする。** apply は plan の `plan_id`(短時間で失効、計画の内容にひもづく)を
  受け取る。計画を見ずに実行はできない。計画が変わった(版が進んだ、ロックが取られた)ら `plan_id` は無効になる。
- `:mutate` 以上は、MCP クライアントの承認(ツール実行の確認)に加えて、**サーバー側でも**
  `plan_id` と、トークンが持つ段階を確かめる。クライアントの承認だけには頼らない。
- `:dangerous`(`WipeRemote` など)は MCP からは**出さない**。人が CLI でのみ実行できる。
- ツールの戻り値は構造化(JSON)で、秘密は取り除かれる。長い出力は要約と、`script_runs` で取る追跡 id に分ける。
- ツールの説明文や、スクリプトの出力に含まれる文字列(リモートの投稿本文など)は**データ**であり、
  AI への指示として扱わない。出力の中に外部由来の文字列が入りうる操作は、戻り値でその項目に `untrusted: true` を付ける。

## 7. 簡易スクリプトの実行

### 7.1 登録

`SukhiFedi.Maintenance.*` のうち、`run(:dry_run | :execute)` の形に従うものを、
モジュール属性(`@sukhi_script`)で宣言して Registry に載せる。

```elixir
@sukhi_script %{
  name: "rebuild_remote_note_ids",
  summary: "リモートの投稿の id を created_at から作り直す",
  modes: [:dry_run, :execute],
  level: :mutate,            # WipeRemote は :dangerous
  lock: :maintenance,
  timeout_ms: 7_200_000,
  options: [skew_s: :integer]
}
```

- 新しいスクリプトを足すとき、宣言を書かなければ**一覧に出ない**(既定で出さない)。
  `eval` の手打ちは当面残るが、手順書は `sukhi script run` に寄せる。
- 任意の Elixir 式を走らせる `sukhi eval '<式>'` は、**既定では無効**。
  有効にするには、サーバー側の環境変数と `:dangerous` 段階のトークン、人の端末(MCP では不可)が要る。
  使われるたびに監査へ式の全文を残す。これは非常口であって、日常の入口ではない。

### 7.2 実行の管理

- **実行履歴**は既存の `maintenance_runs`(`Progress` が書く)を使う。足りない列(依頼した主体、
  引数、終了コード)は追加するが、Datalevin 側のスキーマ(`priv/datalevin/catalog.exs`)にも同じ変更が要る。
  Postgres の移行ファイルを新しく足すかどうかは §12 Q4。
- **同時実行の制限**: `lock` が同じものは同時に一つだけ(`:maintenance` は排他)。取れなければ、
  待たずに即座に失敗して「誰がいつから持っているか」を返す。
- **タイムアウト**: 宣言の値が上限。超えたらキャンセル信号 → 猶予 → 強制終了。強制終了した場合は
  `state: "killed"` として記録し、各スクリプトの冪等性(§7.3)に頼って再実行を促す。
- **実行場所**: 別プロセス(`Task.Supervisor` の子)で動かし、要求元の接続が切れても続ける。
  進み具合は `script runs <id> --follow` で追える。
- **dry-run の結果を実行の条件に使う**(任意): `--execute` は直近の dry-run の要約(件数)を表示し、
  人が確認した件数と大きくずれたら止まる。

### 7.3 スクリプトを書く側の約束

既存のスクリプトがすでにそうしているものを、規則として書く。

1. `run(:dry_run)` は書き込まない。`:execute` と同じ判定で、数だけ返す。
2. 冪等。二度走らせても結果が変わらない(`RebuildRemoteNoteIds` は id が既に合っていれば飛ばす)。
3. `Progress` で進み具合を出す(件ごとではなく、時間で間引かれる)。
4. 戻り値は map。秘密や投稿本文を入れない。

## 8. セキュリティ

### 8.1 認証(どこから呼べるか)

| 入口 | 認証 | 備考 |
| --- | --- | --- |
| Unix ドメインソケット | ファイルの権限(0600、コンテナ内の実行ユーザー)。`docker compose exec` できる人 = 運用者 | **既定の入口。** ネットワークに何も開けない |
| HTTP(任意、既定では無効) | 長い無作為のトークン(`SUKHI_OPS_TOKEN`、ハッシュで保存し、比較は定数時間)+ 送信元の絞り込み | `METRICS_TOKEN` と同じ「未設定なら 404」の方式にする |
| Erlang の cookie | **使わない** | cookie を知れば何でもできるので、シェルの認証には混ぜない |

トークンは複数持てて、それぞれに **段階**と有効期限、名前(「ひなたの Claude Code」など)を持つ。
失効はすぐ効く。発行は人が CLI でのみ行い(MCP からは発行できない)、表示は一度だけ。

### 8.2 権限の段階

| level | できること | 例 |
| --- | --- | --- |
| `:read` | 状態を読む | status, version, audit, script list |
| `:plan` | 計画を作る(副作用なし。外部へ問い合わせはする) | upgrade plan, script dry-run |
| `:mutate` | 実際に変える | upgrade apply, script execute |
| `:dangerous` | 取り返しがつかない、または任意のコード | WipeRemote, eval |

段階は上のほうが下を含む。トークンごとに上限を決める。`:dangerous` は MCP とトークン認証の HTTP から
**そもそも到達できない**(構造で閉じる。呼び出しの中で毎回確かめるのではない)。

### 8.3 秘密情報

- 戻り値・ログ・監査に秘密を出さない。これも一か所:`Ops.Gateway` が返す前に、schema の `secret: true`
  と、既知の環境変数名(`ERLANG_COOKIE`, `*_TOKEN`, `*_KEY`, `SECRET*`)の値を伏せる。
- `status` に環境変数の一覧は出さない。設定の有無(設定済み/未設定)だけ出す。
- 監査にも引数の値は残すが、`secret: true` の引数は伏せる。

### 8.4 監査

- 既存の `admin_audits`(追記専用、DB のトリガで更新と削除を禁止)と**同じ方式**の表を使う。
  列: 時刻、主体(トークン名または `local-socket`)、入口(cli / mcp / http)、操作名、引数(伏せ済み)、
  段階、結果、`plan_id`、`run_id`。
- 変更系だけでなく、`:read` も残す(AI が何を見たかを後で確かめられる)。ただし量が多いので、
  読み取りは「操作名と主体と時刻」だけにして、本文は残さない。
- 監査の書き込みに失敗したら、`:mutate` 以上の操作は**実行しない**(監査なしでは変えない)。
  `:read` は実行し、警告を残す。

## 9. 既存の仕組みをどう使うか(比較)

| 案 | 内容 | 良い点 | 悪い点 | 判断 |
| --- | --- | --- | --- | --- |
| A | `bin/combined rpc` と `eval` をそのまま案内する | 追加実装なし | 任意コード実行。AI に渡せない。出力が文字列。権限と監査なし | 非常口として残す |
| B | `/admin`(Web)に操作を足す | 認証とセッションが既にある。監査もある | ブラウザ前提で、AI と CLI から使いにくい。更新の「コンテナの外」の実施ができない | 表示専用として残す。進み具合は引き続きここ |
| C | **Ops の登録簿 + ソケット + 薄い CLI + MCP(本設計)** | 一か所で定義。人と AI が同じ操作。権限・監査が境界に一つ | 新しく作るもの。ホスト側スクリプトの保守 | **推奨** |
| D | 外部の運用ツール(Ansible, Kamal の hooks, SSH 越しのスクリプト)に寄せる | 実績がある | 項目ごとの権限・MCP・dry-run の統一が弱い。AI 向けの構造化が自前 | 実施の段(§5.1)で Kamal/compose を呼ぶ形で併用 |

再利用するもの: `Release.migrate_all/0` と `check_migration_sanity/0`、`Maintenance.*` と `Progress` と
`maintenance_runs`、`admin_audits` の方式、`rel/env.sh.eex` の fail-closed の考え方、`infra/backup` の検証結果、
`METRICS_TOKEN` の「未設定なら無効」の方式。

## 10. 実装の順番(提案)

後ろの段階は前の段階がなくても有用なように切る。

1. **Registry + ソケット + `status` / `version` / `store info` / `script list|run`**(read と dry-run のみ)。
   既存スクリプトに宣言を足す。`sukhi` のホスト側スクリプト。ここまでで「手打ちの `eval` が要らなくなる」。
2. 監査、同時実行の制限、タイムアウト、実行履歴の拡張。`--execute` を有効にする。
3. `sukhi mcp`(`sukhi-ro` から)。ツール定義の自動生成。
4. `upgrade` / `rollback` の計画と実施(ホスト側)。Watchtower との整理。
5. `sukhi-rw` と `plan_id` による承認。トークンの発行と失効。HTTP(必要なら)。

## 11. やらないこと

- 汎用のリモートシェル、任意コマンドの実行を AI に渡すこと。
- 自動ロールバック。
- Postgres 向けの新しい運用機能(維持のみ)。
- ブラウザの `/admin` を操作の入口に拡張すること。
- Datalevin の内部ファイルを直接操作するコマンド(store の中身は文脈モジュールを通す)。

## 12. 決めたいこと(選択肢と推奨)

**Q1. 想定のとおりでよいか(運用者向けの管理シェルで、コンテナ内の Ops + ホストの `sukhi`)。**
- 推奨: このとおり。違う場合(例: 利用者向けの対話シェル、Fediverse 上のボット操作)は設計の前提が変わる。

**Q2. AI からの接続は、stdio だけで始めるか、HTTP(遠隔)も出すか。**
- 推奨: **stdio だけ**で始める(ネットワークに何も開けない、攻撃面が最小)。遠隔が要る場面が出たら、段階 5 で追加。

**Q3. 更新の経路をどうするか(§5.3)。**
- 推奨: **P**。いまの「sha を選ぶ → タグを書き換える → haloy」を `sukhi release` が包み、事前チェック・事後確認・記録を付ける。
  Watchtower は自前ホスト向けに残し、`sukhi upgrade` は既定を通知のみにする(§5.4)。R(自動デプロイ)は、P が安定してから。

**Q4. 実行履歴の列(依頼元・引数・終了コード)と監査の表を、Datalevin のカタログにだけ足すか、Postgres の移行も足すか。**
- 推奨: **Datalevin のカタログに足し、Postgres は `maintenance_runs` を既存のまま**(新機能の対象にしない方針)。
  Postgres 構成では、監査を構造化ログ(1 行 1 件の JSON)で代える。

**Q5. ロールバックの互換性(戻り先の最低版)を、リリースごとに宣言させるか。**
- 推奨: **宣言させる**(`priv/ops/compat.exs` のような小さな表)。宣言がない版は「スナップショットからの復元のみ」と扱う。
  なお、Datalevin のスキーマ変更が前の版から読めるかの実際の挙動は、この設計では**検証していない**。実装の前に確かめる。

**Q6. `eval` の非常口を残すか。**
- 推奨: **残す**が、既定で無効、`:dangerous`、人の端末のみ、式の全文を監査。完全に無いと、結局 `bin/combined rpc` を直接叩く運用に戻り、監査の外に出る。

**Q7. 署名の検証(cosign)を、更新の必須条件にするか。**
- 推奨: 署名が CI で付くようになるまでは**ダイジェスト一致のみ**を必須にして、「未署名」と明示。付いたら必須にする。

**Q8. コマンド名と置き場所。**
- 推奨: `sukhi`(ホストの `bin/sukhi`)。Elixir 側は `SukhiFedi.Ops.*`。今ある `bin/build-on-box.sh` と同じ階層に置く。

**Q9. haloy 側で確かめたいこと(`sukhi-deploy` を見せてもらえるか)。**
- 見たいのは haloy.yaml のヘルスチェック、ロールバックの手順、image の指定(タグかダイジェストか)、トンネルが要る理由。
- 推奨: 見せてもらう(または該当部分を貼る)。見えないまま設計すると、haloy がすでにしていることを二重に作る。

**Q10. updater(サーバー上の実行役)と信頼の二段(§5.8)。**
- 推奨: 実行役は **ホスト側の小さな updater**(アプリのコンテナの外)。haloy のトークンはそこだけが持つ。
  一次は sigstore(keyless、身元は `combined-sha.yml@refs/heads/main`)、二次はパスキー。
  パスキーの検証は、まず第一段(アプリが検証して署名)で始め、第二段(updater が assertion を自分で検証)へ進める。
- 前提: **CI に署名の工程を足す**(いまはない)。これが入るまで updater は動かさない。
- updater の言語は未決(bash は検証が書きにくく、Go か Elixir が候補)。実装の前に決める。

**Q12. カウントダウンの既定は何分か。取り消し・延長を誰ができるか。**
- 推奨: 既定 10 分(5〜60 分)。取り消しと延長は、パスキー承認ができる管理者なら誰でも。

**Q11. 管理者が複数になったとき、二人承認を入れるか。**
- 推奨: いまは入れない(設計だけ残す)。

**Q13. 第 0 段を「SSH + `sukhi release`」にして、画面(§5.8)は後回しにするか。**
- 推奨: そうする。作るものが最小で、認証は SSH に任せられ、画面が壊れても更新と戻しができる。
  画面は「SSH に入れない人・端末でも更新したい」という要望が出てから足す。
