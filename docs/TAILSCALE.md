# Tailscale で、管理の道をひとまとめにする(Rocky / OCI)

> 状態: 手引きの下書き。コマンドの一部は Tailscale の公式ドキュメント(`install-linux`、`tailscale serve`、auth keys)で確かめたが、
> **実機では試していない。** 画面の名前や、料金・無料枠は変わりうるので、公式を優先する。
> 入口は [`OPERATIONS.md`](OPERATIONS.md)。Cockpit の話は [`RUNTIME.md`](RUNTIME.md) §12。

一度設定すると楽になる、というのが Tailscale のよいところです。
「自分の端末」と「サーバー」を、**インターネットの上に、自分たちだけの小さな網**(tailnet)でつなぎます。
その網の中でだけ、SSH も Cockpit も開く。外からは見えません。

## 1. 何が楽になるか

| これまで(SSH のトンネル) | Tailscale のあと |
| --- | --- |
| Cockpit を見るたびに、トンネルのコマンドを打つ | ブラウザで `https://<箱の名前>.<tailnet>.ts.net` を開くだけ |
| 22 番が公開のまま(総当たりの試行が来る) | 22 番を閉じられる(網の中からだけ) |
| 管理者が増えると、鍵の配り方が増える | 網に入る人を管理画面で足す・外す |
| 箱が増えると、住所や鍵の整理が増える | 名前(MagicDNS)で呼べる |

その代わり、**部品が一つ増え**(`tailscaled`、root で動く)、**提供元の管理の仕組みにも頼ります**(RUNTIME.md §12.5)。
それを分かったうえで、楽さを取る、という選択です。

## 2. 始める前に決めること

- **誰のアカウントで tailnet を作るか。** ログインは、Google や GitHub などの既存のアカウントで行う。
  そのアカウントを失うと、網に入れなくなる。**2 段階認証(できればパスキー)を付ける。**
  管理者が複数なら、1 人のアカウントに頼らない(管理者の追加の方法を、提供元の管理画面で確かめる)。
- **網に入れる人(管理者だけ)**と、**網から届く先**(この箱の SSH と Cockpit だけ)。広く開けない。
- **入れ替わりの手順。** 管理者が抜けるときに、端末を網から外す人は誰か。

## 3. 箱に入れる(Rocky)

公式の簡単な入れ方:

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
```

> 公式の案内では、RHEL・CentOS・Fedora 系もこの方法に対応している。
> ただし、**「ネットから取ってきたものをそのまま実行する」形**なので、箱で使う前に、スクリプトの中身を読むか、
> 公式のパッケージ一覧(`pkgs.tailscale.com` の stable)にある、ディストリごとの**リポジトリ追加の手順**で入れるほうが、
> 手引きの方針(古い作法を土台に)に合う。リポジトリから入れると、OS の自動更新(OPS_PREPARE.md §3)の対象にもなる。

`tailscale up` を実行すると、ログイン用の URL が出る。**手元のブラウザで開いて**、自分のアカウントで認証する。

```bash
tailscale status      # 網に入ったか。自分の端末も見えるか
tailscale ip          # この箱の網の中の IP(100.x.y.z)
```

- `tun` が足りないと言われたら: `sudo modprobe tun`(起動時に読むには `/etc/modules-load.d/tun.conf` に `tun`)。
- OCI のセキュリティリストや firewalld で、**外向きの通信以外を新しく開ける必要は、ふつうない**(一般的な動作。実機で確認)。

## 4. 箱の鍵の期限と札(タグ)

- 箱の鍵(node key)は、既定で **180 日で期限が切れる**(公式の説明)。切れると、網から落ちる。
  サーバーは、**期限なしにする**:管理画面の Machines で、その箱の鍵の期限を切る(または**タグ付き**にする。タグ付きの機器は既定で期限なし)。
- 箱には**タグ**(例: `tag:server`)を付け、**人の端末と区別**する。アクセスのルールは、タグで書く。
- 認証キー(auth key)で自動参加させるなら、**使い切り**(one-off)で、期限を短く。**再利用できるキーは、慎重に**(公式も注意している)。

## 5. 届く範囲を絞る(ACL)

tailnet の既定は「広く届く」ことがあるので、**管理者だけが、この箱の必要な口にだけ**届くように絞る。
書式は管理画面の「Access controls」で、**画面の案内と検証機能を使って書く**(ここに書式は写さない。版で変わるため)。

考え方:

| 誰が | どこへ | 何番 |
| --- | --- | --- |
| 管理者の端末 | `tag:server` | SSH(22)、Cockpit を出すポート(443、§6) |
| それ以外 | (届かない) | ― |

最後に、**別の端末から、届かないはずのところに届かない**ことを確かめる。

## 6. Cockpit を、網の中にだけ出す

Cockpit は `127.0.0.1:9090` で待ち受けたまま(RUNTIME.md §12.1)。そこに `tailscale serve` で橋をかける:

```bash
sudo tailscale serve --bg --https=443 https+insecure://localhost:9090
tailscale serve status          # 出ているか
```

- `https+insecure://` は、Cockpit の自己署名の証明書を受け入れるための印(公式の書式)。
- `serve` は**網の中だけ**。インターネットに出すのは別の `funnel` で、**使わない**。
- `--bg` なら、再起動しても残る。止めるときは `sudo tailscale serve --https=443 off`、全部消すなら `tailscale serve reset`。
- 網の HTTPS 証明書や MagicDNS は、管理画面で有効にしておく必要があるかもしれない(公式の別ページ。**要確認**)。
- 手元のブラウザで `https://<箱の名前>.<tailnet>.ts.net` を開く。Cockpit のログイン画面では、
  **サーバーのアカウントの認証が別に要る**(RUNTIME.md §12.1)。網に入れること = 管理者であること、にはしない。

## 7. SSH も網の中から(任意・慎重に)

```bash
ssh <ユーザーID>@<箱の名前>      # MagicDNS の名前、または 100.x.y.z
```

- Tailscale には、tailnet の身元で SSH を許す機能(`tailscale up --ssh`)もあるが、**最初は使わない**。
  鍵の方針(OPERATING_OVER_SSH.md)を変えずに、**通り道だけ網の中にする**ほうが、ずれが少ない。
- **公開の 22 番を閉じる**のは、次の順で。**閉じる前に、必ず別の道を確かめる:**
  1. 網の中から SSH で入れることを確かめる(22 番はまだ公開のまま)。
  2. 別の端末からも入れることを確かめる。
  3. **OCI の「コンソール接続」で入れることを確かめる**(網が壊れたときの命綱)。
  4. 実際に閉じる(OCI のセキュリティリスト / NSG と firewalld の両方)。
  5. 閉じたあと、網の中からだけ入れて、外からは入れないことを確かめる。

## 8. 日々のこと

- **更新:** `tailscaled` は、直す対象が一つ増えたもの(RUNTIME.md §11)。リポジトリから入れて、OS の自動更新に乗せる。
  脆弱性の知らせは、提供元の告知にも目を通す(週に一度、OPS_MAINTAIN.md §2 に一行足す)。
- **見るところ:** `tailscale status`(箱が網にいるか)、管理画面の Machines(知らない端末がいないか)。
- **端末をなくしたとき:** すぐ管理画面で、その端末を**失効**させる。
- **管理者が抜けるとき:** その人の端末を外し、アカウントの権限を外す。

## 9. 困ったとき

| 症状 | まず見るところ |
| --- | --- |
| 網の中から箱に届かない | `tailscale status`(箱が見えるか)、ACL(§5)、`tailscaled` が動いているか(`systemctl status tailscaled`) |
| 突然、網から落ちた | 鍵の期限(§4)。管理画面で期限を確かめる |
| 22 番を閉じて入れなくなった | OCI のコンソール接続で入り、`tailscaled` を確かめる。**だから §7 の手順 3 が大事** |
| Cockpit が開かない | `tailscale serve status`、`127.0.0.1:9090` で待ち受けているか |

## 10. 提供元に頼りたくないとき

Tailscale のクライアントは公開されているが、制御側(誰がどの端末か、鍵の配り方を管理する側)は提供元の仕組み。
それを自分で持ちたいときは、互換の実装(**Headscale** など。公式とは別のもの)がある。
運用の手間が増えるので、**まずは Tailscale のままで始め**、必要が出たら考える。

## 11. 決めたいこと

1. **Tailscale を使うか。** 推奨: 使う(一度設定すれば楽という判断。手順は上)。ただし最初は **22 番を閉じない**。
   網の中からの SSH と Cockpit が安定してから、閉じるかを決める。
2. **tailnet の持ち主**(誰のアカウントか)と、2 段階認証・管理者の追加の方法。
3. **`tailscaled` をリポジトリから入れる**(スクリプトではなく)。
4. **SSH を Tailscale の身元で許す機能(`--ssh`)**は、使わない(最初は)。
