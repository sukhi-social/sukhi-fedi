# ③ 日々の手入れ(メンテナンス)

> 入口は [`OPERATIONS.md`](OPERATIONS.md)。やさしい考え方は [`CARING_FOR_YOUR_SERVER.md`](CARING_FOR_YOUR_SERVER.md)。
> `sukhi doctor` などは**予定**。手順は読み取りの要約で、**実機では通していない**。

全部を一度にしなくて大丈夫です。**最初の一つは、控えが戻せるかを確かめること。**

## 1. 暦(いつ、何を)

| いつ | すること | 所要 |
| --- | --- | --- |
| **毎日(自動)** | 控えが取られる。**失敗したら通知が来る**ようにしておく | 0 分 |
| **週に一度** | `sukhi doctor`(予定)か、下の「見るところ」を一巡。ログを眺める。ディスクの空き | 10 分 |
| **更新のとき** | OPS_DEPLOY.md。先に控えの新しさを見る | 随時 |
| **月に一度** | OS の更新を反映(カーネルは再起動)。控えから**戻せるか**の確認。使っていない鍵を外す | 30 分 |
| **四半期に一度** | 復元の練習(別の箱で)。権限と連絡先の見直し | 1〜2 時間 |
| **年に一度** | ドメインの更新、証明書の自動更新の確認、手引きの見直し | 1 時間 |

## 2. 見るところ(週に一度)

```bash
docker compose ps                         # すべて動いているか
docker compose logs --since 7d gateway | grep -i "error" | tail -20
df -h /var/lib/sukhi                      # ディスク
sudo systemctl list-timers | grep -E 'sukhi|certbot|dnf'   # 自動のものが動いているか
```

- **配信キュー**が溜まり続けていないか(管理画面のダッシュボード)。
- **メトリクス**: `METRICS_TOKEN` を設定すると `/metrics` が使える。未設定なら 404(出していない、の意味)。
- **おいた枠**(同じ回線の人たちを巻き込むことがある、という懸念が記録されている)で、断った数が急に増えていないか。
- 増えたとき(増えたときだけ)気づけるように、通知を足す。

## 3. 控え(バックアップ)

### 3.1 いまあるもの、ないもの

`infra/backup/` に、restic + B2 + systemd timer の一式がある(毎日 03:17 UTC、検証は日曜 04:30 UTC)。
ただし:

> **いまは dormant(動いていない)で、取る対象は Postgres のダンプ + rustfs + コンテナログ。**
> **Datalevin のデータと SQLite の配信キューは、対象に入っていない。**

主軸が Datalevin なので、**この穴を先に埋める**のが、手引きの最優先の宿題。

### 3.2 Datalevin 構成で取るもの

| もの | 取り方(案・**未確認**) |
| --- | --- |
| Datalevin(`DATALEVIN_DIR`、`graph` を含む) | `dtlv` の複製コマンド(`dtlv copy` で、動いたまま一貫した写しを取れる見込み)。**使い方と一貫性は、実機で確かめる** |
| 配信キュー(SQLite、`SUKHI_QUEUE_DB`) | SQLite の `.backup`(または `VACUUM INTO`)。ファイルを直接コピーしない |
| 原本・メディア | S3 互換の側で複製(rustfs の複製、またはバケットのバージョニング) |
| 設定 | `.env`(秘密を含むので暗号化して、別の場所に) |
| ログ | 任意 |

取った写しを、restic で暗号化して off-host(B2 など)に置く、という形は既存の一式に載せられる見込み。

### 3.3 二軸のリカバリ(取り違えない)

| | 何をする | いつ | データ損失 |
| --- | --- | --- | --- |
| **外科的訂正** | 特定の行だけ直す | 「間違って入った」 | なし |
| **全体の巻き戻し** | 全体を過去の一点へ | ホスト死亡・破損 | その時点以降の良い変更も失う |

普段欲しいのはほぼ外科的訂正([`data-correction.md`](data-correction.md))。
**外部(他サーバー由来)のデータは、復元ではなく捨てて作り直す**のが第一手。内部(自分のサーバーが生んだもの)は取り返せないので、控えで守る。

### 3.4 控えが「戻せる」と確かめる(いちばん大事)

控えは、**戻せて初めて控え**です。

1. 月に一度: 最新の控えから、別の場所(別のディレクトリ、または別の箱)に**取り出す**。
2. 中身を開いて、データが読める(件数が合う)ことを見る。
3. 四半期に一度: 別の箱に**実際に立ち上げて**、ログインできるところまで。
4. 結果を、短く記録する(日付と、できたか)。

## 4. 更新のメンテナンス

- **アプリ:** OPS_DEPLOY.md。
- **OS の部品:** 自動の安全更新に任せる(OPS_PREPARE.md §3)。月に一度、再起動が必要か見る(`needs-restarting -r`、Debian は `/var/run/reboot-required`)。
- **コンテナの土台:** アプリの更新を待たずに焼き直す仕組みが要る(RUNTIME.md §11。定期の再ビルド・走査は**未実装**)。
  それまでは、**image が焼かれてから 30 日を超えたら、更新を考える**という目安を持つ。
- **証明書:** certbot のタイマーが更新する。年に一度、`certbot renew --dry-run` で確かめる。

## 5. データと容量

- **Datalevin:** `DATALEVIN_MAP_SIZE_MB`(既定 1024)は上限。データが近づく前に上げる。
- **graph の掃除:** `SUKHI_GRAPH_SWEEP` は既定で**予行**。`execute` にすると、期限を過ぎた他サーバーのデータを消す。
  先に予行のログを見てから。TTL の既定は、フォロー中の人 90 日、それ以外 14 日。
- **ログ:** `infra/logrotate` で回す。ディスクを食い続けていないか、週に一度。
- **保守スクリプト**(`SukhiFedi.Maintenance.*`): **予行が先**。`run(:dry_run)` で数を見て、よければ `run(:execute)`。
  実行は `bin/sukhi_fedi rpc`(予定の `sukhi script run` に置き換わる)。長いものは tmux の中で。

## 6. 人のこと

- **告知:** 更新、メンテナンス、困りごとは、先にお知らせを。やさしい言葉で、急かさずに。
- **通報:** 届いたら、責めずに、まず事実を見る。手当ては軽いほうから(COMMUNITY_SUPPORT.md §2)。
- **問い合わせ:** 窓口を一つ決めて、公開しておく(メール、Matrix)。
- **鍵とパスキー:** 使っていない管理者の鍵・トークンは、月に一度、外す。

## 7. 困ったとき(落ち着いて)

1. **まず止まる。** 深呼吸。直すより先に、状況を書き留める(時刻、見えているもの)。
2. **控えの新しさを確かめる。** いまの状態の控えも、触る前に取っておく。
3. **軽い手から。** ログ → 再起動 → 前の版に戻す → 控えから復元、の順。
4. **聞く。** Matrix `#sukhi-social:matrix.org` に、書き留めた状況と一緒に。一人で決めなくて大丈夫。
5. **あとで振り返る。** 責める場ではなく、次の手引きを良くする場として、短く書く。

| 症状 | 見るところ |
| --- | --- |
| 全部が遅い | ディスクの空き、メモリ(`DATALEVIN_XMX`、BEAM)、配信キュー |
| 配信が溜まる | 相手のサーバーが落ちている可能性。まず待つ。キューのログ |
| 管理画面に入れない | セッションの有効期限、パスキー、トークンの失効 |
| ディスクが満杯 | ログ、古い控えの一時ファイル、graph の掃除(予行から) |
| 起動時に落ちる | `ERLANG_COOKIE`、`DOMAIN`、Datalevin のディスクと権限 |
