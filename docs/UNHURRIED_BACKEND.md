# バックエンドを、ゆったりさせる(速さのための仕組みの棚おろし)

> 状態: **一回目の棚おろし。** 見つけたものを並べて、素直にできたものは直し、
> 迷うものは「決めたいこと」に残した。web-next のように、急かさず、読んで追える形へ。

## 読みの前提

「ゆったり」には二つの意味を込めた。

1. **挙動がおだやか。** 無駄な再試行や連打をしない。待つときは静かに待つ。エラーは責めない。
2. **コードが素直。** 速さのために足された近道が、読む人の頭の中で二重になっていない。

[`CODE_STYLE.md`](CODE_STYLE.md) の「安全や速さは一か所に置く」は、このままにする。
その一か所が、**ひとつだけ**になっているかを見直した、というのがこの文書。
バッチ取得(`*_for_notes` など)は、外すと N+1 になって、速さだけでなく待ちも荒くなるので、触らない。

## 棚おろし

直感の損ない: ○ ほぼなし / △ 少し / ✕ 読むのに骨が折れる。

## 直したもの

**自前の「期限つき ETS」を、HotCache ひとつにした(#1〜#3)。**
同じ形の仕組みが、四か所に別々の書き方で住んでいた。`HotCache.fetch/3` と
`HotCache.forget/1`(プロフィール更新で数を忘れる)の二つだけで読めるようになった。
副作用として、テスト設定の `hot_cache: false` が効くので、古い答えが次のテストに残らない。
数の持ち時間は同じ(counts 60 秒、dashboard 30 秒、map 5 秒)。
期限の粒度は秒になったので、実際の持ち時間は `ttl` の半分〜`ttl` になる。

**`Store.concurrently/1` を外した(#4)。** home の二つの問い合わせを、順番に聞くだけにした。
経路が DB で変わらない。待ちに上限がない `Task.async_stream` もなくなった。
遅くなるのは Datalevin の home だけで、実機(0.5 OCPU)での差は未計測。

触っていないもの: `/proxy/` を窓の数えから外した件、メディア取得の 30 秒の期限、
counts がダイレクトを数えない件(コメントごと残してある)。

## 決めたいこと

**A. トークンの 60 秒(#8, #9)。** 二枚の層(api 側の `TokenCache` と、ゲートウェイ側の
`RateIdentity`)が、同じ問いを別々に覚えている。一枚にするとわかりやすいが、
どちらかの層を外すと、認証つきの読み取りが毎回 RPC か DB になる。
実機で測ってから決めるのがよさそう。失効の遅れを 60 秒から縮めたいかも、一緒に。

**B. 画像の二段構え(#10)。** AVIF を裏で焼いて、できるまで WebP を返す仕組み。
一番ややこしい。「WebP だけ、その場で」にすれば読みやすく、帯域は少し増える。
Cloudflare の手前に置く前提なら効きが変わるので、運用の見立てを聞きたい。

**C. 実機の測り。** 0.5 OCPU で #4 と上の変更がどれくらい響くか。
`.github/workflows/load-bench.yml` で見られる。
