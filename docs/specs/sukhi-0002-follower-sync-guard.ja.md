# sukhi-0002: フォロワー一覧の安全な突き合わせ

- 状態: 草案。`delivery/lib/sukhi_delivery/delivery/followers_sync.ex` に実装済み。
- 識別子: `https://sukhi.social/spec/sukhi-0002/1`
- 土台にする仕様: FEP-8fcf(フォロワー一覧の同期)
- 用語と「必須・推奨・任意」の意味: [README.ja.md](README.ja.md)

## 一言で

他のサーバのユーザーを、こちらのユーザーがフォローしているかどうかの記録を、突き合わせて直す仕組みがあります。その直し方で、**一覧が空のとき、または一部しか見えないときは、何も消さない**、と決めた仕様です。

## 何が困るのか

FEP-8fcf では、送り手が「フォロワーの一覧から計算した短い値(ダイジェスト)」を添えて配送します。受け手は、自分の記録から同じ値を計算して比べます。値が違えば、「どちらかの記録がずれている」と分かります。

ここまでは決まっています。決まっていないのは、**ずれが見つかったとき、どう直すか**です。

- 一覧を取りに行ったら、空だった。→ 本当に誰もいないのか、取得に失敗しただけなのか、区別できない。
- 一覧がページに分かれていて、最初の一ページしか読めなかった。→ 残りのページのフォロー関係は、「一覧にない」のか「まだ読んでいない」のか分からない。

この状態で「一覧にないものを消す」と、本当は残すべき関係を消してしまいます。

## 用語

**ローカルの関係**: フォローする側がこのサーバにいる関係。控えもなく、相手のサーバから取り直すこともできない。消すと、元に戻せない。

## 規則

1. 取得した一覧が**空**なら、何も消さない(**必須**)。
2. 一覧がページに分かれ、全部は読めていない(**一部しか見えない**)なら、何も消さない(**必須**)。
3. 配送元の actor が自分のサーバのものなら、その配送は処理しない(**必須**)。自分の共有受信箱に戻ってきた配送で、ローカルの関係を変えてはいけない。
4. ダイジェストが違い、一覧が**完全に読めた**ときだけ、一覧にない関係を消してよい(**任意**)。この作業は、受信箱の返事とは別に実行するのが**任意**(返事を先に返すため)。
5. 消されずに残った古い関係は、そのままにしてよい。相手が `Undo(Follow)` を送ったときに消える。

## 理由

間違い方は二通りあります。

| 間違い | 結果 | 元に戻せるか |
| --- | --- | --- |
| 残すべき関係を消す | その人のタイムラインから、黙って投稿が消える | 戻せない |
| 消すべき関係を残す | 一件余分に配送される | 戻せる(あとで Undo で消える) |

戻せない間違いを避けるために、戻せる間違いの方を選んでいます。

## 送る側

FEP-8fcf のとおり。ローカルの actor が共有受信箱へ送る配送に、`Collection-Synchronization` ヘッダを付ける。中身は、`collectionId`、`url`、そして承認済みフォロワーの URI を並べ替えた一覧の SHA-256 ダイジェスト。
