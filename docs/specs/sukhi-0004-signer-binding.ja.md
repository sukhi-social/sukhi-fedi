# sukhi-0004: 署名した者と、名乗った者の結び付け

- 状態: 草案。`web/inbox_controller.ex:51-97` と `ap/instructions`(`trusted_inline_origin?/2`)に実装済み。
- 識別子: `https://sukhi.social/spec/sukhi-0004/1`
- 土台にする仕様: ActivityPub の受信箱への配送、RFC 9421、draft-cavage-12
- 用語と「必須・推奨・任意」の意味: [README.ja.md](README.ja.md)

## 一言で

署名が正しいことは、「その activity を送ってよい人が送った」ことの**証明にはなりません**。署名を調べるだけでなく、**署名した者が、activity の中で名乗っている actor と結び付いている**ことまで確かめる、という仕様です。

## 何が困るのか

論理で書くと、こうです。

- P: 「この署名は、ある鍵で作られたものとして正しい」
- Q: 「この activity は、中に書かれた actor が送ったものだ」

署名の検証が確かめるのは P だけです。P ならば Q、とは限りません。たとえば、悪意のあるサーバ X が、自分の鍵で正しく署名した activity の中に、`actor: 他のサーバ Y のユーザー` と書いても、署名は正しいままです。Y のユーザーを装えてしまいます。

同じことが、activity の中に埋め込まれた投稿(インラインのオブジェクト)にも言えます。X が、Y の投稿のふりをした内容を埋め込めます。

そこで、P に加えて、「署名した者」と「名乗っている actor」が同じ持ち主だ、という条件 R を確かめます。P かつ R ならば、Q を信じてよい、という形にします。

## 規則

1. 本文を読む(解析する)**前**に、署名を検証する(**必須**)。
2. 署名が間違っている、または付いていないときは、401 を返し、その activity を実行しない(**必須**)。
3. 検証のあと、署名した者を特定できている(`keyId` と、その鍵の持ち主)ようにする(**必須**)。
4. 名乗っている `actor` のホストが、署名した者のホストと違うときは、activity に埋め込まれたデータを信用しない(**必須**)。そのデータは、持ち主の元から取り直すか、無視する。
5. 署名を検証するときの URL は、設定した公開ドメインから作るのが**推奨**。リクエストの `Host` ヘッダは使わない。中継のプログラムが書き換えるため。
6. ブロック中のドメインからの activity は、202 を返して、何も処理せずに捨ててよい(**任意**)。送り手に「ブロックされている」と気づかせないため。
7. FEP-8b32 の証明(`proof`)があり、検証できるときは、検証に失敗したら 401 を返す(**必須**)。HTTP 署名にもどって通してはいけない。証明がない、または未対応の暗号方式だけのときは、すでに通った HTTP 署名にもどる。証明の鍵の `controller` は、activity の `actor` と同じでなければならない(**必須**)。

## 理由

- 規則 3 と 4 は、R を確かめるためのものです。2026 年 6 月の点検で、署名だけを確かめて R を確かめていない穴が見つかり、塞ぎました(`FEDERATION.md` §3)。
- 規則 7 は、「確かめられる証明が間違っていたのに、見なかったことにする」道をなくすためのものです。
