# sukhi-0001: 署名方式のやりなおし

- 状態: 草案。`delivery/lib/sukhi_delivery/delivery/sig_spec.ex` と `worker.ex` に実装済み。
- 識別子: `https://sukhi.social/spec/sukhi-0001/1`
- 土台にする仕様: RFC 9421(HTTP Message Signatures)、draft-cavage-http-signatures-12
- 用語と「必須・推奨・任意」の意味: [README.ja.md](README.ja.md)

## 一言で

サーバに activity を送るとき、HTTP の署名を付けます。署名の書き方には二種類あり、相手がどちらを受けるかは、送ってみるまで分かりません。そこで、まず片方で送り、**400 か 401 が返ったときだけ**もう片方で一度だけやりなおします。うまくいった方式は、その相手について覚えておきます。

## 何が困るのか

二つの方式を A(RFC 9421)と B(cavage、古い書き方)とします。相手は、A だけ受ける、B だけ受ける、両方受ける、のどれかです。

- いつも A だけで送ると、「B だけ」の相手には届きません。
- いつも A と B の両方を送ると、すべての相手への通信量が二倍になります。
- どちらの仕様にも、「相手がどちらを受けるか」を知る方法は書かれていません。

だから、「やってみて、拒否されたら変える」という手順を決めておく必要があります。

## 送る側の規則

1. 初めての相手には、A で送るのが**推奨**。どちらから始めてもよいが、次の 2 があるから、通信は成り立つ。
2. 相手の受信箱が **400 か 401** を返したら、同じ activity を、もう一方の方式で**一度だけ**送りなおすことが**必須**。
   - 理由: これがないと、送り手と受け手に共通の方式がないとき、永久に通信できない。
3. それ以外の状態(403、404、410、429、5xx など)では、やりなおさないのが**推奨**。
   - 理由: これらは「方式が違う」という意味ではない。やりなおしても直らず、通信量が増えるだけ。
4. 二回目で受け入れられたら、その方式をその相手について覚えておくのが**推奨**。覚えておく期間は 7 日にしてよい(**任意**)。期限が切れたら、1 に戻る。
5. 二回とも拒否されたら、何も覚えないのが**推奨**。
   - 理由: 方式の問題なら、片方は通るはず。両方だめなら、原因は鍵、時計のずれ、ブロックのどれかで、方式ではない。
6. 覚えている間は、一回の配送につき一回だけ送るのが**推奨**。

### 条件をまとめると

相手が受ける方式の集合を S とします。A と B のどちらかが S に入っているなら、この手順は 2 回以内に届きます。覚えたあとは、毎回 1 回で届きます。S が空なら、2 回とも拒否されるので、5 により何も覚えません。

## 署名に含める項目

- A(RFC 9421): `@method @target-uri @authority host date content-digest`
- B(cavage): `(request-target) host date digest content-type`
- 本文のあるリクエストでは、その方式のダイジェストの項目を**署名に含める**ことが**必須**。「ヘッダがある」だけでは足りない。
  - 理由: ダイジェストが署名の対象でなければ、本文を別のものに差し替えても署名は正しいままになる。

## 受ける側の規則

1. `Signature-Input` ヘッダがあれば A として、なければ B として検証する(**必須**)。
2. 本文のあるリクエストで、ダイジェストが署名の対象に入っていなければ拒否する(**必須**)。
3. 時計のずれの許容は、300 秒以上にするのが**推奨**。sukhi は 3600 秒。
4. 署名を拒否するときは、400 か 401 を返す(**必須**)。
   - 理由: 送り手が「規則 2 のやりなおし」をするかどうかを、この状態で判断するから。他の状態を返すと、送り手はやりなおせない。

## 相手の actor を取得するとき

署名付きの GET(actor の取得)は、いつも B で送ってよい(**任意**)。sukhi はそうしている。いま確認できた相手はすべて B を受けるため。その状態が変わったら見直す。

## 未解決のこと

- RFC 9421 には、受け取れる方式を知らせる `Accept-Signature` がある。ActivityPub のサーバで送るものは確認できていないので、この仕様は頼っていない。
- 7 日という値は、コードの設定から取ったもので、実測に基づいてはいない。
