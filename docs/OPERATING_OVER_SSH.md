# サーバーを SSH で運用する(はじめての人向け)

> 状態: **案内書の下書き。** 中で呼ぶ `sukhi` コマンドは、まだ実装がない
> ([`SERVER_SHELL.md`](SERVER_SHELL.md) の設計)。実装されるまでは、§5 の「いまの手順」を使う。
> 箱の住所・ユーザー名・鍵の置き場は、各自の環境の値に読み替えること。

サーバーの管理者は、ブラウザの画面だけでなく、**サーバーの中に入って自分の手で確かめられる**ほうがいい。
画面が壊れた夜に、最後に頼れるのはここだから。この文書は、そのための入口を、順番に書いたもの。
わからないところで止まっても大丈夫。戻る道は、そのつど書いてある。

## 1. 先に、ひとことで

```
ssh <あなたのユーザー>@<サーバー>      # 入る
sukhi status                          # いまの様子を見る
sukhi release                         # 更新の計画を見る(まだ何も変わらない)
sukhi release --execute               # 確認して、更新する
exit                                  # 出る
```

それだけ。以降は、それぞれの意味と、困ったときの話。

## 2. 入る前に: 鍵を用意する

SSH は「パスワード」ではなく「鍵」で入るのがおすすめ。鍵は二つに分かれた対(つい)になっていて、
**秘密鍵**は手元から出さず、**公開鍵**だけをサーバーに置く。

```bash
ssh-keygen -t ed25519 -C "あなたの名前@使うPC"
```

- 保存先は、そのまま Enter でよい(`~/.ssh/id_ed25519`)。
- **パスフレーズ(鍵の鍵)は付ける。** 秘密鍵のファイルが盗まれても、すぐには使われない。
- 作られた `id_ed25519.pub` が公開鍵。サーバーの持ち主(または自分)が、サーバーの
  `~/.ssh/authorized_keys` に一行足す。**`id_ed25519`(.pub のない方)は、誰にも渡さない。**
- さらに安全にしたいなら、セキュリティキー(FIDO2)に入った鍵もある: `ssh-keygen -t ed25519-sk`。
  キーを挿して触れないと入れなくなる。

毎回パスフレーズを打つのが大変なら、`ssh-agent` に覚えさせる(閉じるまで覚えていてくれる)。

```bash
ssh-add ~/.ssh/id_ed25519
```

## 3. 入る

名前を決めておくと、毎回長く打たなくて済む。`~/.ssh/config` に:

```
Host sukhi
    HostName <サーバーの住所>
    User <あなたのユーザー>
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
```

そして:

```bash
ssh sukhi
```

**はじめて入るとき**、こう聞かれる:

```
The authenticity of host '…' can't be established.
ED25519 key fingerprint is SHA256:…
Are you sure you want to continue connecting (yes/no)?
```

これは「このサーバーは本物ですか」という確認。表示された指紋(`SHA256:…`)を、
サーバーの持ち主から別の手段(チャットなど)で教えてもらったものと**見比べてから** `yes` と答える。
見比べないで通すと、偽のサーバーに入ってしまう道が開く。二回目からは何も聞かれない。

入れないとき:

| 出たもの | 意味 | することと |
| --- | --- | --- |
| `Permission denied (publickey)` | 公開鍵がサーバーに置かれていない、またはユーザー名が違う | 公開鍵を渡し直す。`ssh -v sukhi` で理由が見える |
| `Connection timed out` | 住所が違う、ネットワークが閉じている | 住所とトンネルの要否を確かめる(箱が閉じている場合は、先にトンネルを張る) |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 前回と指紋が違う | **進まずに止まる。** サーバーを作り直したのか、何かが挟まっているのか、持ち主に確かめる |

## 4. 切れても大丈夫にする: tmux

更新の途中でネットワークが切れると、入っていた画面ごと止まってしまうことがある。
**`tmux`** は、切れても裏で動き続ける画面。更新などの長いものは、この中でやる。

```bash
tmux new -s sukhi        # 画面を作る(名前は何でも)
# …ここで作業…
# Ctrl-b を押して、離してから d  →  画面から離れる(裏で動き続ける)
tmux attach -t sukhi     # 戻る
```

`sukhi release --execute` は、tmux の中でなくても途中で止まらないように作る予定だが、
手元の癖として、長いものは tmux の中で。

## 5. 更新する

### 5.1 `sukhi` ができたあと(目指す形)

```bash
sukhi release
```

何も変えずに、**計画**だけが出る。読むところ:

- **何を上げるか**: いまの版 → 新しい版、変更の要約、image のダイジェスト
- **署名の確認**: 「このリポジトリの main が焼いたもの」と確かめられたか(§SERVER_SHELL 5.8)
- **データへの影響**: マイグレーションがあるか、戻せるか
- **前提**: 直近のバックアップが新しいか、ディスクに余裕があるか、キューが詰まっていないか
- **止まる時間**: 短い再起動がある

読んで、よければ:

```bash
sukhi release --execute
```

もう一度、**上げる版の番号を打ち直す**ように求められる(`y` ではなく)。
流し読みで通らないための仕掛け。通ったら、利用者への告知が出て、決めた分数のあとに更新される。
途中で止めたくなったら、同じ画面から取り消せる:

```bash
sukhi release cancel
```

終わったら `sukhi status` で、新しい版が名乗っていて、キューが流れていることを確かめる。
おかしければ `sukhi release rollback`(これも、計画を見て、確認してから)。

### 5.2 いまの手順(`sukhi` ができるまで)

いまの本番(haloy で入れ替えている場合)は、次の形で動いている(詳しくは `SERVER_SHELL.md` §5.0)。
Compose で動かしている場合は、[`RUNTIME.md`](RUNTIME.md) §5 の手順を使う。

1. main に push すると、GitHub Actions が `sha-<commit>` というタグで image を GHCR に出す(自動)。
2. 手元で、デプロイ用のリポジトリ(sukhi-deploy)の `haloy.yaml` にある image のタグを、新しい `sha-…` に書き換える。
   **四つの image(combined / anubis / natadeco-ssr / web-next)を、すべて同じ sha にする。**
3. `haloy deploy -t <ターゲット>`。
4. 終わったら、サイトを開いて、`/admin` の様子とログを見る。

困ったら、ここで止まって、戻す: 前の `sha-…` に書き戻して、もう一度 `haloy deploy`。
**データベースの変更を含む版だった場合は、書き戻すだけでは戻らないことがある**(§SERVER_SHELL 5.6)。
そのときは、バックアップから戻す前に、必ず誰かに相談する。

## 6. 見るためのコマンド(読むだけ。壊さない)

```bash
sukhi status             # 版、稼働時間、store、キュー
sukhi store info         # データの置き場所とサイズ、直近のバックアップ
sukhi script list        # 実行できる保守スクリプトの一覧
sukhi script runs        # 実行の履歴と進み具合
sukhi audit --since 1d   # 一日の操作の記録
```

どれも、何も変えない。迷ったらまずここ。

## 7. 保守スクリプトを実行する

```bash
sukhi script list
sukhi script run rebuild_remote_note_ids            # 何もしない。何件が対象かだけ出る
sukhi script run rebuild_remote_note_ids --execute  # 実際に変える
```

- **何も付けなければ、必ず「予行」(dry-run)**。数と見込みだけが出て、書き込まない。
- 予行の数が思ったとおりか、見てから `--execute`。
- 一度に動かせるのは一つだけ。ほかのものが動いていれば、断られて、誰がいつから動かしているかが出る。
- 長いものは `sukhi script runs <id>` で進み具合が見られる。止めたいときは `sukhi script cancel <id>`。
- 取り返しのつかないもの(リモートデータの消去など)は、`sukhi` では実行できず、
  別の明示の手順になる。

## 8. 守ってほしいこと

- **秘密鍵(`id_ed25519`)は、人に渡さない。** チャットにも貼らない。
- **サーバーの中で見えるもの(環境変数、鍵、トークン)を、画面共有やログに載せない。** `sukhi` は秘密を伏せて出すが、
  `env` や `cat` で直接見たものは、そのまま出る。
- **本番のデータを、手で直接書き換えない。** 保守スクリプトを使えば、記録と進み具合が残る。
- **操作は記録される。** 「誰が責められるか」のためではなく、「何が起きたかを後から一緒に読める」ために。
- わからないときは、**止まって聞く**。`--execute` を付けなければ、いつでも安全に試せる。

## 9. 出るとき

```bash
exit
```

tmux の中なら、先に `Ctrl-b` → `d` で離れるか、`exit` で画面ごと閉じる。
